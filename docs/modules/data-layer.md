# Data layer

Supabase Postgres accessed through PostgREST (`@supabase/supabase-js`). No ORM. See `docs/QUERY_OPTIMIZATION.md` before
writing queries.

## Database schema (confirmed)

The following DDL is the authoritative source for the three tables the application uses. All types, defaults,
constraints, triggers, and indexes are listed here so query authors and reviewers can reason about the schema without
connecting to Supabase.

### `game_status`

Lookup table for library states (e.g. "En progreso"). Drives the filter tabs on `/games`.

```sql
create table public.game_status
(
  id                     bigint generated by default as identity not null,
  name                   text null,
  created_at             timestamp with time zone                not null default now(),
  games_with_this_status integer                                 not null default 0,
  constraint game_status_pkey primary key (id),
  constraint game_status_name_key unique (name)
) TABLESPACE pg_default;
```

- `games_with_this_status` is maintained by the `trigger_update_game_status_count` trigger below.

### `games`

Catalog of games played on stream. Community-averaged vote stats (`avg_vote`, `vote_count`) are maintained by the
`on_vote_change` trigger — the app never aggregates votes itself.

```sql
create table public.games
(
  id             bigint generated by default as identity not null,
  created_at     timestamp with time zone                not null default now(),
  name           text null,
  game_status_id bigint null default '11'::bigint,
  cover_url      text null,
  avg_vote       numeric(4, 2) null default 0,
  vote_count     integer null default 0,
  constraint games_pkey primary key (id),
  constraint games_game_status_id_fkey foreign KEY (game_status_id)
    references game_status (id) on update CASCADE on delete set null
) TABLESPACE pg_default;
```

- Default `game_status_id` is `11` — new games land in that status unless explicitly set.
- `avg_vote` is `numeric(4, 2)` — max `99.99`, two decimal places.
- `game_status_id` is nullable and set to NULL on parent delete (orphaned games are preserved).

### `games_user_votes`

One row per `(user_id, game_id)` pair. A `null` vote means the user cleared their vote (row is kept).

```sql
create table public.games_user_votes
(
  id         bigint generated by default as identity not null,
  created_at timestamp with time zone                not null default now(),
  user_id    uuid null,
  game_id    bigint null,
  vote       smallint null,
  constraint games_user_votes_pkey primary key (id),
  constraint games_user_votes_user_id_game_id_key unique (user_id, game_id),
  constraint games_user_votes_game_id_fkey foreign KEY (game_id)
    references games (id) on update CASCADE on delete CASCADE,
  constraint games_user_votes_user_id_fkey foreign KEY (user_id)
    references auth.users (id) on update CASCADE on delete CASCADE,
  constraint check_vote_range check (
    (vote is null) or ((vote >= 1) and (vote <= 10))
    )
) TABLESPACE pg_default;

create index IF not exists games_user_votes_game_id_idx
  on public.games_user_votes using btree (game_id) TABLESPACE pg_default;
```

- `vote` is `smallint` — range 1–10, or `null` (cleared).
- Unique `(user_id, game_id)` enables upsert semantics.
- `game_id_idx` index supports the trigger's aggregation lookup.
- Cascade deletes: removing a game or user removes the vote row.

### Triggers

```sql
-- Keeps game_status.games_with_this_status in sync with row counts
create trigger trigger_update_game_status_count
  after INSERT or
DELETE
or update on games
for each row execute function handle_game_status_count_change();

-- Keeps games.avg_vote and games.vote_count in sync with votes
create trigger on_vote_change
  after INSERT or
DELETE
or update on games_user_votes
for each row execute function update_game_vote_stats();
```

- `trigger_update_game_status_count` → `handle_game_status_count_change()`: updates `game_status.games_with_this_status`
  after any change to `games`.
- `on_vote_change` → `update_game_vote_stats()`: recomputes `games.avg_vote` and `games.vote_count` after any vote
  change.

## Clients

| Client                 | File               | Key                               | Use                                                    |
|------------------------|--------------------|-----------------------------------|--------------------------------------------------------|
| Per-request SSR client | `lib/db-client.ts` | `PUBLIC_SUPABASE_PUBLISHABLE_KEY` | Auth + data queries in page frontmatter & API routes   |
| Browser client         | `lib/db-client.ts` | `PUBLIC_SUPABASE_PUBLISHABLE_KEY` | Direct DB writes + reads from client `<script>` blocks |

The SSR client is created per request (not shared) so each call carries the user's cookies/JWT. The browser client is a
singleton using the publishable key — safe for the browser when RLS policies are in place. Both fall back to a valid
placeholder URL/key when env is absent so import-time `createClient` can't crash the page. Intentional — keep it.

## Writes

`games_user_votes` is the only table written from `src/`:

- `lib/client/games-vote.ts` - inserts, updates, or clears a vote via the browser Supabase client (`upsert` on
  `user_id,game_id`). Authenticated via the synced SSR session (`setSession`); the `user_id` comes from the
  authenticated user, never from user input. A `vote` of `null` clears the vote (row kept, `vote` column set to null).
  After a successful write the same module re-fetches the community average for that game (`fetchCommunityAverage`)
  and updates the card — there is no optimistic average math in the UI.

## Community-vote averages & the `games` trigger

The community average + vote count shown on `/games` is **read from the `games` table**: `lib/games.ts`
(`loadGamesLibrary`) selects `vote_count, avg_vote` alongside the grid columns, and `buildCommunityAverages` maps
them per game. The `on_vote_change` trigger (function `update_game_vote_stats()`) keeps those columns in sync after
every INSERT/UPDATE/DELETE on `games_user_votes` — the app never aggregates votes itself.

The client reads the same columns after a vote too: `lib/client/games-vote.ts` (`fetchCommunityAverage`) queries
`games` for `vote_count, avg_vote` and updates the card. This requires an RLS policy allowing authenticated users to
SELECT `games` (the same policy the SSR page relies on).

Display format: whole numbers render as integers, otherwise max 1 decimal (e.g. `8` or `8.5`).

## Reads are server-side

All queries run in `.astro` frontmatter or API routes. Do not fetch from the client. Handle `error` defensively and
default to `[]` (existing pattern).

### `/api/games/search` (GET)

Global name search + pagination for the `/games` grid. Queried by the browser grid controller
(`lib/client/games-grid.ts`)
as the user types (debounced) and when future lazy-loading fetches the next page. The search term survives every page
fetch, so lazy loading always appends results matching the current term.

- Params: `q` (name substring, case-insensitive `ilike`), `offset`, `limit` (capped at 48, default 24).
- Returns: `{ games: GameListRow[], count: number }` — `count` is the total matching rows (drives the "X de Y juegos"
  counter).
- Accent-insensitive matching ("pokemon" → "Pokémon") is **not** implemented — it needs the Postgres `unaccent`
  extension + a functional index on `games(name)`. Flagged as follow-up.
